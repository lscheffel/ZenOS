# AED-00010

# Canonical Repository Layout

---

# Status

**Proposed**

Normative.

---

# 1. Purpose

This AED defines the canonical physical organization of the repository.

Directory layout SHALL emerge from architecture.

Architecture SHALL NOT emerge from directory layout.

---

# 2. Core Principle

The filesystem is an implementation.

The architecture is the system.

Changing directories SHALL NOT change architectural meaning.

---

# 3. Repository Top-Level Domains

The repository SHALL be organized into architectural domains.

Recommended canonical structure:

```text
repository/

├── core/
├── governance/
├── knowledge/
├── capabilities/
├── project/
├── runtime/
├── extensions/

├── AGENTS.md
├── REGISTRY.md
├── BOOT.md
└── README.md
```

Only domains appear at the repository root.

Everything else belongs to a domain.

---

# 4. Core Domain

Purpose:

Implements repository infrastructure.

Recommended layout:

```text
core/

    identity/

    kernel/

    boot/

    registry/

    discovery/

    resolver/

    loader/

    lifecycle/
```

Core SHALL remain implementation-independent.

---

# 5. Governance Domain

Purpose:

Defines repository behavior.

Recommended layout:

```text
governance/

    directives/

    constraints/

    policies/

    standards/

    decisions/

    reviews/
```

Governance SHALL contain no runtime information.

---

# 6. Knowledge Domain

Purpose:

Stores architectural understanding.

Recommended layout:

```text
knowledge/

    architecture/

    ontology/

    glossary/

    specifications/

    references/

    patterns/

    history/
```

Knowledge SHALL remain canonical.

---

# 7. Capabilities Domain

Purpose:

Contains executable repository behavior.

Recommended layout:

```text
capabilities/

    agents/

    skills/

    workflows/

    validators/

    generators/

    analyzers/

    transformers/

    templates/
```

Subdirectories represent Capability specializations.

Not architectural domains.

---

# 8. Project Domain

Purpose:

Contains business implementation.

Examples:

```text
project/

    source/

    documentation/

    tests/

    releases/

    assets/
```

Repository architecture SHALL remain independent from project implementation.

---

# 9. Runtime Domain

Purpose:

Stores transient execution state.

Examples:

```text
runtime/

    session/

    workspace/

    cache/

    state/

    tasks/

    logs/
```

Runtime SHALL remain disposable.

---

# 10. Extensions Domain

Purpose:

Supports repository evolution.

Examples:

```text
extensions/

    integrations/

    plugins/

    adapters/

    experiments/
```

Extensions SHALL remain isolated.

---

# 11. Root Documents

The repository root SHOULD remain intentionally small.

Recommended root artifacts:

---

## README.md

Repository introduction.

---

## AGENTS.md

Repository operating instructions.

---

## BOOT.md

Repository initialization.

---

## REGISTRY.md

Canonical repository inventory.

---

Additional files SHOULD be minimized.

---

# 12. Directory Independence

Directories SHALL organize implementation.

Directories SHALL NOT define semantics.

Semantics SHALL originate from:

- Ontology
- Contracts
- Registry
- Metadata

Moving files SHOULD NOT change architectural meaning.

---

# 13. Metadata

Every architectural directory SHOULD expose metadata.

Examples include:

Purpose

Owner

Scope

Dependencies

Consumers

Version

Lifecycle

Directories SHOULD become self-describing.

---

# 14. Repository Navigation

Preferred navigation:

```text
Boot

↓

Registry

↓

Contract

↓

Metadata

↓

Implementation
```

Discouraged navigation:

```text
Filesystem

↓

Search

↓

Guess

↓

Open files
```

Repository evolution SHALL prefer semantic navigation.

---

# 15. Layout Invariants

---

## LAY-001

Every top-level directory SHALL represent an architectural domain.

---

## LAY-002

Runtime SHALL remain isolated.

---

## LAY-003

Governance SHALL remain centralized.

---

## LAY-004

Knowledge SHALL remain canonical.

---

## LAY-005

Capabilities SHALL remain modular.

---

## LAY-006

Repository SHALL remain self-describing.

---

## LAY-007

Filesystem SHALL remain secondary.

---

# 16. Architectural Smells

The following indicate repository degradation.

- domain duplication
- project knowledge inside governance
- runtime inside knowledge
- duplicated capability implementations
- directories defining architecture
- undocumented root artifacts
- repository-wide miscellaneous folders
- uncontrolled top-level growth

These SHOULD trigger architectural review.

---

# 17. Future Evolution

The canonical layout MAY evolve.

Future implementations MAY replace directories with:

- graph databases
- registries
- semantic indexes
- object stores
- distributed repositories

The conceptual domains SHALL remain stable.

---

# 18. Decision

This AED establishes the canonical repository layout.

Directory organization SHALL reflect architectural responsibilities.

The physical repository SHALL remain a projection of the logical architecture.

Architecture SHALL always remain the source of truth.

---

# 19. Foundational Principle

> **Repositories are not trees of files.**

> **Repositories are graphs of knowledge projected onto filesystems.**

The filesystem is merely one possible serialization of the repository architecture.

Future implementations MAY adopt different storage technologies without changing the conceptual model defined by this specification.
