# ADR-00006 — Documentation Platform Migration

## Status

**Accepted**

---

# Decision Statement

ZenOS documentation SHALL evolve from a **repository-oriented documentation model** into a **documentation-first platform**, where GitHub Pages becomes the canonical documentation interface while GitHub remains the canonical development platform.

This ADR establishes the target architecture governing that migration.

Execution is intentionally excluded from this document and is delegated to **TODO-ADR-00006.md**.

---

# Context

The current documentation architecture originated as a repository companion.

As the platform evolved, documentation progressively accumulated architectural content, governance artifacts and navigation responsibilities without a corresponding evolution of its information architecture.

Current limitations include:

- homepage behaves as a repository README
- navigation depends heavily on GitHub
- documentation is repository-centric
- internal links frequently leave the documentation site
- GitHub Pages is underutilized
- information architecture is shallow
- onboarding experience is weak
- navigation hierarchy is implicit
- documentation lacks domain-oriented entry points

The current architecture no longer reflects the maturity level of ZenOS.

---

# Decision

ZenOS SHALL adopt a Documentation-First Architecture.

The published documentation SHALL become the preferred interface for readers.

The repository SHALL remain the preferred interface for contributors.

Documentation SHALL be organized around information architecture rather than repository structure.

---

# Design Principles

## Documentation First

Documentation SHALL be independently navigable.

Users SHALL never need GitHub in order to browse documentation.

---

## Single Source of Truth

Documentation SHALL avoid duplicated knowledge.

Architectural decisions belong exclusively to ADRs.

Execution belongs exclusively to TODO documents.

Repository implementation belongs exclusively to repository artifacts.

---

## Stable Information Architecture

Navigation SHALL be designed independently from repository implementation details.

Repository evolution SHALL minimally impact user navigation.

---

## Progressive Disclosure

Landing pages SHALL provide orientation.

Detailed information SHALL reside in dedicated pages.

---

## Relative Navigation

Internal documentation SHALL use relative links whenever possible.

Repository URLs SHALL only be used when intentionally directing readers outside the documentation portal.

---

## Domain-Oriented Organization

Documentation SHALL be organized according to logical domains rather than filesystem convenience.

---

# Target Information Architecture

The documentation SHALL expose the following primary navigation domains.

```
docs/

index.md

getting-started.md

architecture.md

repository.md

governance/

knowledge/

capabilities/

runtime/
```

Each domain SHALL expose its own landing page.

Example:

```
governance/

index.md

directives/

decisions/

constraints/

policies/

standards/

templates/
```

Equivalent structures SHALL exist for the remaining major domains.

---

# Homepage Responsibilities

The homepage SHALL function as an entry portal.

It SHALL provide orientation rather than exhaustive documentation.

Recommended sections include:

- Hero
- Platform Overview
- Quick Start
- Repository Architecture
- Core Domains
- Boot Sequence
- Core Documents
- Repository Links

The homepage SHALL NOT become an index of every repository document.

---

# Navigation Model

Navigation SHALL be hierarchical.

Recommended flow:

```
Homepage

↓

Domain

↓

Collection

↓

Document
```

Every document SHALL belong to a discoverable navigation path.

---

# Link Strategy

Preferred

```
relative links
```

Preferred

```
Jekyll links
```

Discouraged

```
absolute GitHub blob URLs
```

Forbidden for internal navigation

- raw.githubusercontent links
- GitHub blob links
- GitHub tree links replacing documentation navigation

---

# GitHub Pages

GitHub Pages SHALL become the canonical publishing mechanism.

Configuration SHALL explicitly define:

- url
- baseurl
- permalink strategy
- markdown engine
- plugins
- relative links

Configuration SHALL remain deterministic.

---

# Repository Cleanup

Migration SHALL eliminate obsolete artifacts, including but not limited to:

- legacy redirects
- obsolete HTML entry points
- duplicated navigation
- dead documentation
- orphan pages

Only artifacts participating in the publishing pipeline SHALL remain.

---

# Acceptance Criteria

Migration SHALL be considered complete when:

- documentation is documentation-first
- homepage is portal-oriented
- all domains expose landing pages
- internal navigation is self-contained
- GitHub dependency is minimized
- documentation hierarchy is stable
- relative links are adopted
- obsolete artifacts removed
- deterministic builds preserved

---

# Consequences

## Positive

- professional documentation platform
- improved discoverability
- cleaner navigation
- improved onboarding
- easier maintenance
- stable URLs
- future-proof information architecture
- reduced architectural coupling

## Negative

- migration effort
- hyperlink refactoring
- temporary coexistence of legacy artifacts during migration
