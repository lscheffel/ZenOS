# AED-00001

# Repository Architectural Vision & Foundational Principles

---

# Status

**Proposed**

This document is normative.

Whenever conflicts exist between this AED and lower-level documentation, this AED SHALL prevail.

---

# 1. Executive Summary

This repository SHALL evolve into a reusable operating framework for autonomous software engineering.

It SHALL NOT be treated as a collection of prompts.

It SHALL NOT be organized around any particular LLM.

It SHALL NOT depend upon any single agent runtime.

Instead, this repository SHALL become a model-independent operating layer responsible for organizing:

* knowledge;
* governance;
* capabilities;
* contracts;
* execution;
* lifecycle;
* architectural consistency.

Prompts, skills, commands and agents are implementation details.

The architecture itself is the product.

---

# 2. Context

Current generations of AI development environments are heavily centered around prompts.

Prompt-centric architectures suffer from predictable failure modes:

* duplicated knowledge;
* undocumented assumptions;
* prompt drift;
* context explosion;
* model lock-in;
* inconsistent behavior;
* semantic entropy.

As repositories evolve, prompts become increasingly difficult to maintain because they simultaneously encode:

* architecture;
* governance;
* implementation;
* workflows;
* conventions;
* project knowledge.

These concerns evolve at different rates.

Treating them as one artifact inevitably produces architectural degradation.

This AED proposes a different approach.

Knowledge shall become architecture.

Architecture shall become executable.

---

# 3. Vision

The repository SHALL behave as an operating system for AI agents.

An operating system does not solve business problems.

Instead, it provides stable abstractions allowing applications to solve business problems.

Likewise, this repository SHALL provide stable abstractions for autonomous software engineering.

Agent runtimes may change.

Language models may change.

Editors may change.

Tooling may change.

The repository architecture SHOULD remain largely unaffected.

---

# 4. Primary Goal

The primary goal is not writing code.

The primary goal is minimizing ambiguity.

Every architectural decision SHALL be evaluated according to one question:

> Does this reduce ambiguity for future agents?

If the answer is negative, the decision SHOULD be reconsidered.

---

# 5. Architectural Philosophy

This repository recognizes six immutable truths.

## Truth 1

Knowledge is an asset.

Knowledge SHALL be explicitly represented.

Knowledge SHALL never depend upon human memory.

---

## Truth 2

Ambiguity is technical debt.

Every ambiguity eventually manifests as inconsistent execution.

Reducing ambiguity is therefore equivalent to reducing technical debt.

---

## Truth 3

Structure outlives implementation.

Prompts change.

Models change.

Tools change.

Architecture survives.

Repository evolution SHALL prioritize structural stability over implementation convenience.

---

## Truth 4

Explicit systems outperform implicit systems.

Hidden assumptions SHALL be considered architectural defects.

---

## Truth 5

Discovery is superior to inference.

Agents SHOULD discover information.

Agents SHOULD NOT infer repository structure.

Repository knowledge SHALL describe itself.

---

## Truth 6

Governance precedes execution.

Execution without governance produces entropy.

Governance SHALL therefore be treated as a first-class architectural concern.

---

# 6. Long-Term Vision

The repository SHALL gradually evolve toward the following conceptual model.

```text
               Language Model
                      │
               Agent Runtime
                      │
         ─────────────────────────
           Repository Operating Layer
         ─────────────────────────
                      │
       Governance • Contracts • Discovery
       Policies   • Ontology  • Lifecycle
                      │
              Capability Layer
                      │
              Project Artifacts
                      │
                 Source Code
```

The operating layer is the architectural product.

Everything below it is replaceable.

---

# 7. Core Architectural Principles

The following principles are immutable.

---

## AP-001

### Single Source of Truth

Every concept SHALL possess one canonical definition.

Duplicate semantic definitions SHALL be eliminated.

References SHALL replace duplication.

---

## AP-002

### Separation of Concerns

Different responsibilities SHALL be represented independently.

Examples include:

* governance;
* ontology;
* contracts;
* project knowledge;
* execution;
* runtime state.

Mixing concerns increases entropy.

---

## AP-003

### Progressive Knowledge Loading

Agents SHALL load only the minimum amount of knowledge necessary.

Knowledge SHALL become available progressively.

Repository initialization SHOULD resemble operating system bootstrapping rather than loading an entire encyclopedia.

---

## AP-004

### Declarative Architecture

Whenever possible, architecture SHALL be described declaratively.

Preferred artifacts include:

* Markdown specifications;
* manifests;
* contracts;
* metadata;
* registries.

Procedural prompts SHOULD become progressively smaller over time.

---

## AP-005

### Explicit Contracts

Every executable artifact SHALL expose an explicit contract.

Implicit interfaces SHALL be treated as defects.

---

## AP-006

### Explicit Constraints

Behavioral limits SHALL always be documented.

Agents SHOULD never infer operational boundaries.

---

## AP-007

### Discoverability

Knowledge SHALL be discoverable.

Repository navigation SHALL NOT depend upon directory exploration.

---

## AP-008

### Low Cognitive Load

Repository evolution SHALL minimize:

* unnecessary context;
* duplicated reading;
* token consumption;
* semantic overlap.

---

## AP-009

### Model Independence

The repository SHALL remain independent from any specific language model.

No architectural decision SHALL assume:

* GPT
* Claude
* Gemini
* KiloCode
* Codex

as permanent dependencies.

---

## AP-010

### Anti-Entropy

Repository entropy SHALL continuously decrease.

Architectural evolution SHOULD remove complexity faster than it introduces new complexity.

---

# 8. Architectural North Star

The following statement defines the long-term objective of this repository.

> **An AI agent SHALL never need to guess how the repository works.**
>
> **The repository SHALL explain itself.**

This sentence SHOULD guide every future architectural decision.

---

# 9. Non-Goals

This repository is NOT intended to become:

* a prompt collection;
* a template repository;
* a documentation repository;
* a coding standard;
* a language-specific framework.

Those concerns MAY exist inside the repository.

They SHALL NOT define its architecture.

---

# 10. Consequences

Adopting this AED implies future architectural evolution toward:

* explicit contracts;
* modular governance;
* progressive discovery;
* canonical ontology;
* lifecycle management;
* capability-based organization;
* manifest-driven navigation.

This AED intentionally does not define implementation details.

Implementation SHALL be addressed by subsequent AEDs.

# 12. Final Principle

The repository SHALL evolve toward becoming a self-describing operating system for autonomous software engineering.

Every future decision SHOULD move the architecture closer to that objective.

If a future change increases ambiguity, duplicates knowledge or strengthens coupling to a specific model, that change SHOULD be considered architecturally inconsistent with this vision.
