# AED-00007

# Canonical Contract Specification

---

# Status

**Proposed**

Normative.

---

# 1. Purpose

This AED establishes the universal Contract Model for the repository.

Every architectural Entity SHALL expose a Contract.

Contracts SHALL become the primary interface through which Humans and AI Agents understand repository components.

Contracts SHALL replace implicit assumptions.

---

# 2. Motivation

Large repositories fail because knowledge becomes implicit.

Agents begin to infer:

* purpose
* ownership
* dependencies
* responsibilities

Inference introduces ambiguity.

Architecture SHALL eliminate inference wherever possible.

Contracts transform assumptions into explicit knowledge.

---

# 3. Core Principle

Entities SHALL NOT explain themselves through implementation.

Entities SHALL explain themselves through Contracts.

Implementation is mutable.

Contracts define identity.

---

# 4. Universal Rule

Every Entity SHALL possess one Contract.

Every Contract SHALL describe exactly one Entity.

One Entity.

One Contract.

No exceptions.

---

# 5. Repository Contract Model

Conceptually:

```text
Entity

↓

Contract

↓

Implementation
```

Consumers SHALL depend upon Contracts.

Consumers SHOULD NOT depend upon implementation details.

---

# 6. Scope

The following Entities SHOULD expose Contracts.

* Capability
* Artifact
* Workflow
* Policy
* Directive
* Constraint
* Standard
* Template
* Specification
* AED
* Registry
* Manifest

Future Entity types SHALL follow the same model.

---

# 7. Mandatory Contract Fields

Every Contract SHOULD define the following information.

## Identity

Defines:

* Identifier
* Name
* Version

---

## Purpose

Defines:

* Why this Entity exists.

---

## Responsibilities

Defines:

* What the Entity owns.

---

## Non-Responsibilities

Defines:

* What the Entity intentionally does not own.

This field reduces architectural drift.

---

## Inputs

Defines required information.

---

## Outputs

Defines produced information.

---

## Dependencies

Defines consumed Entities.

---

## Consumers

Defines expected users.

Examples:

* Agent
* Human
* Workflow
* Capability

---

## Preconditions

Defines what MUST already be true.

---

## Postconditions

Defines what SHALL become true.

---

## Failure Conditions

Defines invalid execution scenarios.

---

## Invariants

Defines conditions that SHALL always remain true.

---

## Authority

Defines architectural authority.

Examples:

Repository-wide

Project-only

Runtime-only

Experimental

---

## Lifecycle

Defines maturity.

---

## Review Cycle

Defines expected revision cadence.

---

# 8. Contract Semantics

Contracts SHALL describe behavior.

Contracts SHALL NOT describe implementation.

Correct:

> Produces architectural decisions.

Incorrect:

> Opens file X, then calls Tool Y.

Implementation belongs elsewhere.

---

# 9. Contract Inheritance

Specialized Entities SHALL inherit Contract semantics.

Example:

```text
Entity

↓

Capability

↓

Skill
```

The Skill SHALL inherit the Capability Contract.

Specializations MAY extend Contracts.

They SHALL NOT violate inherited semantics.

---

# 10. Contract Stability

Contracts SHALL evolve slower than implementation.

Frequent Contract changes indicate unstable architecture.

Repository evolution SHOULD prioritize stable Contracts.

---

# 11. Contract Discoverability

Contracts SHALL be self-describing.

An Agent SHOULD determine:

* purpose
* ownership
* dependencies
* lifecycle

without reading implementation.

Reading implementation SHOULD become exceptional.

---

# 12. Contract Composition

Complex systems SHALL emerge through Contract composition.

Example:

Workflow

↓

Skill A

↓

Validator

↓

Generator

↓

Reporter

Each Entity exposes one Contract.

The Workflow understands the system through Contracts.

Not through implementation.

---

# 13. Contract Compatibility

Repository evolution SHOULD preserve backward compatibility whenever practical.

Breaking Contract changes SHOULD require explicit architectural review.

Breaking implementation MAY be acceptable.

Breaking Contracts SHALL be considered high impact.

---

# 14. Repository ABI

Conceptually, Contracts form the repository Application Binary Interface.

Humans read Markdown.

Agents consume Contracts.

Implementations remain replaceable.

Contracts remain stable.

---

# 15. Contract Invariants

---

Every Entity SHALL expose one Contract.

---

## CON-002

---

## CON-003

---

## CON-004

Contracts SHALL remain implementation-independent.

---

## CON-005

Contracts SHALL expose explicit dependencies.

---

## CON-006

Contracts SHALL expose explicit boundaries.

---

## CON-007

Contracts SHALL expose explicit lifecycle.

---

## CON-008

Contracts SHALL remain discoverable.

---

# 16. Architectural Smells

The following indicate Contract degradation.

* undocumented responsibilities;
* undocumented ownership;
* implicit dependencies;
* hidden assumptions;
* Contracts duplicated across Entities;
* implementation leaking into Contracts;
* Contracts redefining governance;
* multiple Contracts describing the same Entity.

Future refactoring SHOULD eliminate these progressively.

---

# 17. Future Evolution

Markdown SHALL remain the canonical authoring format.

Future implementations MAY expose Contracts through:

* metadata;
* manifests;
* machine-readable indexes;
* registries;
* APIs;
* MCP resources.

The Contract model SHALL remain unchanged.

---

# 18. Decision

This AED establishes Contracts as the canonical interface of the repository.

Future architectural evolution SHALL prioritize Contract stability over implementation stability.

Every architectural subsystem SHALL communicate primarily through Contracts.

Implementation SHALL become secondary.

---

# 19. Architectural Consequences

Adopting this AED changes repository philosophy.

Repository understanding SHALL progressively move away from reading implementation.

Instead:

Repository

↓

Discovery

↓

Contract

↓

Decision

↓

Implementation

The repository becomes self-describing.

---

# 20. Foundational Principle

> **Architecture is not the collection of files.**

> **Architecture is the collection of Contracts governing those files.**

When Contracts remain stable, implementations may evolve indefinitely without degrading the operating model.

This principle SHALL guide every future architectural decision regarding repository evolution.
