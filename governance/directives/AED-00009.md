# AED-00009

# Context Loading Architecture

---

# Status

**Proposed**

Normative.

---

# 1. Purpose

This AED defines the repository memory model.

Repository context SHALL become an architectural subsystem.

Context SHALL be treated as managed memory.

Context SHALL NOT be treated as accumulated conversation.

---

# 2. Motivation

Current AI systems continuously accumulate context.

This produces:

- token explosion
- duplicated knowledge
- degraded reasoning
- contradictory information
- inconsistent execution

The repository SHALL instead manage context explicitly.

---

# 3. Core Principle

Agents SHALL load context.

Agents SHALL NOT accumulate context.

Loading implies intentional selection.

Accumulation implies entropy.

---

# 4. Repository Memory Model

Repository memory is divided into independent layers.

```text
Persistent Memory

↓

Session Memory

↓

Working Memory

↓

Execution Context

↓

Output
```

Every layer has different responsibilities.

---

# 5. Persistent Memory

Represents long-lived architectural understanding.

Examples:

- Vision
- AEDs
- Ontology
- Governance
- Contracts

Persistent Memory changes rarely.

It SHOULD remain immutable during execution.

---

# 6. Session Memory

Represents information relevant for one repository session.

Examples:

Current project

Loaded capabilities

Selected workflow

Repository configuration

Session Memory MAY change.

It SHOULD remain small.

---

# 7. Working Memory

Represents active reasoning.

Contains only information necessary to solve the current task.

Working Memory SHALL remain minimal.

Information no longer required SHOULD be discarded.

---

# 8. Execution Context

Represents immediate execution state.

Examples:

Current file

Current artifact

Current capability

Current operation

Execution Context SHOULD remain extremely small.

---

# 9. Context Hierarchy

Context SHALL load from stable to volatile.

```text
Identity

↓

Architecture

↓

Ontology

↓

Governance

↓

Contracts

↓

Capability Metadata

↓

Working Set

↓

Execution
```

Loading SHALL stop whenever sufficient context has been acquired.

---

# 10. Working Set

The Working Set is the smallest complete context required for one task.

It SHALL contain:

- required knowledge
- required contracts
- required governance
- required capabilities

Nothing more.

The Working Set SHALL be disposable.

---

# 11. Lazy Loading

Knowledge SHALL be loaded on demand.

Repository components SHOULD remain unloaded until explicitly required.

Loading SHALL always prefer metadata before implementation.

---

# 12. Context Eviction

Context SHALL be discarded when no longer necessary.

Repository implementations SHOULD support:

Least Recently Used

Least Frequently Used

Task Completion

Explicit Reset

Architecture SHALL remain independent from eviction strategy.

---

# 13. Context Reuse

Previously loaded context MAY be reused.

Reused context SHALL remain valid.

Invalidated context SHALL be reloaded.

---

# 14. Context Boundaries

Every execution SHALL define explicit context boundaries.

Agents SHALL know:

What has been loaded.

What has not been loaded.

What assumptions remain invalid.

Implicit context SHALL be avoided.

---

# 15. Context Invariants

---

## CTX-001

Persistent Memory SHALL remain canonical.

---

## CTX-002

Working Memory SHALL remain minimal.

---

## CTX-003

Execution SHALL consume Working Memory.

---

## CTX-004

Execution SHALL NOT depend upon historical conversation.

---

## CTX-005

Knowledge SHALL be progressively loaded.

---

## CTX-006

Context SHALL remain disposable.

---

## CTX-007

Repository understanding SHALL emerge from explicit loading.

---

# 16. Architectural Smells

The following indicate context degradation.

- loading entire repositories
- recursive documentation reading
- duplicated context
- permanent runtime notes
- unnecessary capability loading
- implementation before metadata
- historical conversations treated as architecture

These patterns SHOULD be eliminated.

---

# 17. Future Evolution

Future repository implementations MAY expose intelligent context loaders.

Examples:

Semantic loading

Dependency-aware loading

Graph traversal

Vector retrieval

Registry-assisted loading

Adaptive working sets

Architecture SHALL remain unchanged.

---

# 18. Decision

Repository context SHALL become a managed architectural resource.

Loading SHALL replace accumulation.

Working Sets SHALL replace monolithic prompts.

Repository execution SHALL progressively minimize context consumption while maximizing architectural awareness.

---

# 19. Foundational Principle

> **Context is memory.**

> **Memory is managed.**

> **Managed memory scales.**

The repository SHALL therefore treat context as a managed architectural resource rather than conversational history.
