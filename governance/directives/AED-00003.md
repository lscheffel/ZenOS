# AED-00003

# Canonical Repository Ontology

---

# Status

**Proposed**

Normative.

---

# 1. Purpose

This AED establishes the canonical language of the repository.

Repository architecture SHALL communicate using concepts rather than implementation-specific terminology.

Every architectural artifact SHALL use the definitions established herein.

No artifact SHALL redefine repository terminology.

---

# 2. Motivation

Language precedes architecture.

Architecture precedes implementation.

When terminology is inconsistent:

* governance becomes ambiguous;
* capabilities overlap;
* documentation diverges;
* agents infer different meanings.

The repository SHALL therefore maintain one canonical ontology.

---

# 3. Foundational Principle

Words SHALL represent concepts.

Concepts SHALL remain stable.

Implementations MAY evolve.

Terminology SHALL NOT.

---

# 4. Core Concept Model

The repository recognizes only a small number of first-class concepts.

Everything else SHALL derive from them.

```text
Repository

├── Domain
│
├── Entity
│
├── Artifact
│
├── Capability
│
├── Contract
│
├── Policy
│
├── Directive
│
├── Constraint
│
├── Workflow
│
├── State
│
├── Knowledge
│
└── Runtime
```

No future concept SHOULD duplicate an existing one.

---

# 5. Canonical Definitions

---

## Repository

The complete operating environment.

Contains every architectural concern.

A repository is NOT a folder.

A repository is a self-describing operating environment.

---

## Domain

A stable architectural responsibility.

Examples:

* Governance
* Knowledge
* Runtime
* Project

Domains organize concepts.

They do not execute work.

---

## Entity

The smallest meaningful architectural object.

Examples:

* Artifact
* Capability
* Policy

Everything represented inside the repository SHALL be an Entity.

---

## Artifact

Persistent information.

Artifacts store knowledge.

Examples include:

* AED
* Specification
* Guide
* Template
* Documentation

Artifacts do not execute.

---

## Capability

A reusable operational behavior.

Capabilities perform work.

Examples include:

* Agent
* Skill
* Command
* Workflow
* Generator
* Validator

Every executable object SHALL be a Capability.

---

## Contract

A formal interface describing an Entity.

Contracts define:

* purpose
* responsibilities
* inputs
* outputs
* dependencies
* invariants

Contracts describe behavior.

They do not implement behavior.

---

## Policy

Organizational expectations.

Policies define preferred behavior.

Policies SHOULD be followed.

Policies MAY be overridden through explicit decisions.

---

## Directive

Mandatory architectural behavior.

Directives define what SHALL happen.

Directives are normative.

---

## Constraint

An explicit limitation.

Constraints define what SHALL NOT happen.

Constraints reduce ambiguity.

---

## Workflow

An ordered sequence of Capabilities.

Workflows orchestrate execution.

Workflows do not replace Capabilities.

---

## State

The current lifecycle position of an Entity.

States SHALL be explicit.

Hidden states SHALL NOT exist.

---

## Knowledge

Persistent architectural understanding.

Knowledge survives execution.

Knowledge accumulates over time.

---

## Runtime

Temporary operational context.

Runtime SHALL remain transient.

Runtime SHALL NOT become long-term documentation.

---

# 6. Derived Concepts

The following concepts derive from the canonical ontology.

---

## Agent

A specialized Capability responsible for autonomous reasoning.

---

## Skill

A reusable Capability focused on one responsibility.

---

## Command

A user-invoked Capability.

---

## Template

A Capability that produces standardized Artifacts.

---

## Specification

An Artifact defining expected behavior.

---

## AED

An Artifact documenting architectural decisions.

---

## Manifest

An Artifact describing repository discovery.

---

## Registry

An Artifact enumerating canonical repository objects.

---

## Glossary

An Artifact documenting ontology.

---

# 7. Semantic Relationships

Repository concepts SHALL follow the relationships below.

```text
Repository

contains

Domains

contain

Entities

Entities expose

Contracts

Capabilities consume

Knowledge

Capabilities obey

Governance

Governance defines

Policies
Directives
Constraints

Artifacts preserve

Knowledge

Runtime tracks

State
```

These relationships SHALL remain stable.

---

# 8. Naming Rules

Architectural vocabulary SHALL remain singular.

Preferred examples:

Capability

Artifact

Contract

Workflow

Policy

Directive

Constraint

Avoid creating synonymous concepts.

For example:

Do not create:

Prompt

Instruction

Recipe

Macro

Automation

if the intended meaning is simply:

Capability

Vocabulary expansion SHOULD be resisted.

---

# 9. Ontological Invariants

The following statements SHALL always remain true.

---

## INV-001

Everything represented by the repository SHALL be an Entity.

---

## INV-002

Every executable Entity SHALL be a Capability.

---

## INV-003

Every persistent Entity SHALL be an Artifact.

---

## INV-004

Every Capability SHOULD expose a Contract.

---

## INV-005

Every Artifact SHOULD expose metadata.

---

## INV-006

Every Entity SHOULD possess a lifecycle.

---

## INV-007

No Entity SHALL possess multiple semantic identities.

---

# 10. Anti-Patterns

The following patterns indicate ontological drift.

* multiple names for the same concept;
* commands behaving like policies;
* documentation acting as runtime;
* prompts acting as governance;
* skills redefining ontology;
* artifacts implementing behavior;
* workflows replacing capabilities.

Future refactoring SHOULD eliminate these patterns.

---

# 11. Evolution Rule

New concepts SHALL only be introduced when they cannot be represented by existing concepts.

Creating vocabulary is considered an architectural change.

Architectural changes SHALL require explicit review.

---

# 12. Decision

This AED establishes the canonical semantic model of the repository.

All future AEDs SHALL use this ontology.

No architectural document SHALL redefine these concepts.

This ontology becomes the official language of the repository.

Future implementations MAY evolve freely, provided they preserve the semantic model defined herein.

---

# 13. Foundational Principle

> The repository SHALL evolve by expanding capabilities, not by expanding vocabulary.

A stable language enables a stable architecture.

A stable architecture enables autonomous systems.

Therefore, semantic stability SHALL be considered a first-class architectural objective.
