# AED-00008

# Repository Boot & Discovery Architecture

---

# Status

**Proposed**

Normative.

---

# 1. Purpose

This AED defines how AI Agents initialize repository awareness.

Repository discovery SHALL become deterministic.

Agents SHALL progressively discover the repository.

Agents SHALL NOT explore the repository.

---

# 2. Motivation

Traditional AI workflows perform unrestricted filesystem exploration.

Typical sequence:

Filesystem

↓

find

↓

grep

↓

open files

↓

infer architecture

↓

execute

This approach introduces:

- excessive token consumption
- duplicated reads
- inconsistent understanding
- architectural ambiguity
- runtime variability

The repository SHALL invert this model.

---

# 3. Core Principle

The repository SHALL describe itself.

Agents SHALL consume repository metadata.

Agents SHALL NOT infer repository organization.

---

# 4. Boot Philosophy

Boot SHALL be deterministic.

Every agent entering the repository SHOULD receive the same architectural understanding.

Repository awareness SHALL emerge through explicit discovery.

Never through exploration.

---

# 5. Repository Components

Repository initialization is composed of two independent mechanisms.

## Repository Registry

Defines everything that exists.

Permanent.

Canonical.

Repository-wide.

---

## Boot Manifest

Defines what SHALL be loaded.

Dynamic.

Context-sensitive.

Minimal.

---

# 6. Repository Registry

The Registry is the canonical inventory.

It SHALL describe:

- Domains
- Entities
- Contracts
- Capabilities
- Policies
- Directives
- Standards
- Templates
- Specifications
- Relationships

The Registry SHALL NOT contain implementation.

It contains references only.

---

# 7. Boot Manifest

The Boot Manifest defines the minimum initialization context.

Examples:

Repository identity

Current architecture version

Required AEDs

Required governance

Required ontology

Required capabilities

The Boot Manifest SHOULD remain extremely small.

---

# 8. Discovery Sequence

Repository initialization SHALL conceptually follow:

```text
Agent

↓

Boot Manifest

↓

Repository Identity

↓

Repository Registry

↓

Ontology

↓

Governance

↓

Contracts

↓

Capabilities

↓

Execution
```

Skipping steps SHOULD require explicit justification.

---

# 9. Progressive Discovery

Knowledge SHALL be loaded progressively.

Recommended order:

Identity

↓

Architecture

↓

Ontology

↓

Governance

↓

Contracts

↓

Capability Metadata

↓

Capability Implementation

↓

Project Knowledge

↓

Runtime

Every step SHOULD minimize context consumption.

---

# 10. Repository Identity

Identity SHALL answer only:

Who am I?

What is my purpose?

What architecture version do I implement?

Nothing else.

Identity SHALL remain stable.

---

# 11. Discovery Rules

Discovery SHALL answer questions.

Examples:

Where is Capability X?

↓

Registry

What governs Capability X?

↓

Contract

What knowledge is required?

↓

Metadata

What implementation exists?

↓

Artifact

The filesystem SHALL become the last step.

---

# 12. Loading Rules

Agents SHOULD load:

metadata first

implementation second

Only if necessary.

Repository evolution SHOULD minimize implementation loading.

---

# 13. Repository Indexes

The repository MAY expose specialized indexes.

Examples:

Capability Index

Artifact Index

AED Index

Policy Index

Contract Index

Workflow Index

Indexes SHALL reference canonical entities.

Indexes SHALL NOT duplicate knowledge.

---

# 14. Discovery Invariants

---

## DIS-001

Repository SHALL explain itself.

---

## DIS-002

Registry SHALL remain canonical.

---

## DIS-003

Boot SHALL remain deterministic.

---

## DIS-004

Discovery SHALL precede execution.

---

## DIS-005

Metadata SHALL precede implementation.

---

## DIS-006

Agents SHOULD avoid filesystem exploration.

---

## DIS-007

Progressive loading SHALL minimize context.

---

# 15. Architectural Smells

The following indicate discovery degradation.

- recursive directory traversal
- loading entire repositories
- duplicated indexes
- implementation before metadata
- manual discovery
- hidden entry points
- undocumented capabilities

Future refactoring SHOULD eliminate these patterns.

---

# 16. Future Evolution

The discovery model SHALL remain independent from storage technology.

Possible implementations include:

- Markdown
- Registry files
- Graph databases
- Vector indexes
- MCP Resources
- Semantic indexes

Architecture SHALL remain unchanged.

---

# 17. Decision

Repository discovery SHALL become metadata-driven.

Filesystem traversal SHALL become an implementation detail.

Registry SHALL become the authoritative repository inventory.

Boot Manifest SHALL become the authoritative initialization document.

Together they SHALL define deterministic repository initialization.

---

# 18. Foundational Principle

> **Repositories should be discovered.**

> **Not explored.**

Repository evolution SHALL continuously reduce filesystem dependency and increase semantic discoverability.
