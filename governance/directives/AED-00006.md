# AED-00006

# Capability Model

---

# Status

**Proposed**

Normative.

---

# 1. Purpose

This AED defines the canonical execution model of the repository.

Every executable behavior SHALL be represented as a Capability.

This AED intentionally replaces implementation-specific concepts such as:

* Agent
* Skill
* Command
* Workflow
* Prompt
* Macro
* Automation

with one canonical abstraction.

---

# 2. Motivation

Current AI ecosystems introduce different terminology for similar concepts.

Examples:

Claude Code → Command

Cursor → Rule

KiloCode → Skill

OpenAI → Tool

MCP → Tool

Gemini → Prompt

Although terminology differs, the architectural responsibility remains identical:

> Execute behavior.

The repository SHALL therefore define one canonical abstraction.

---

# 3. Definition

A Capability is an executable architectural Entity.

Capabilities consume knowledge.

Capabilities obey governance.

Capabilities produce outcomes.

Capabilities SHALL NOT own architectural knowledge.

---

# 4. Core Responsibilities

Every Capability SHALL:

* perform work;
* expose a contract;
* consume governance;
* consume knowledge;
* produce outputs;
* report execution state.

Capabilities SHALL NOT:

* redefine ontology;
* redefine governance;
* persist runtime;
* duplicate architectural knowledge.

---

# 5. Capability Hierarchy

The repository recognizes one root abstraction.

```text
Capability
│
├── Agent
│
├── Workflow
│
├── Skill
│
├── Command
│
├── Validator
│
├── Generator
│
├── Analyzer
│
├── Transformer
│
└── Template
```

Future execution models SHOULD specialize Capability instead of introducing unrelated concepts.

---

# 6. Agent

An Agent is a reasoning-oriented Capability.

Characteristics:

* autonomous
* adaptive
* context-aware
* planning-oriented

Agents coordinate work.

Agents SHOULD consume other Capabilities.

---

# 7. Workflow

A Workflow orchestrates multiple Capabilities.

A Workflow SHOULD NOT implement behavior directly.

Instead, it coordinates existing Capabilities.

---

# 8. Skill

A Skill performs one focused responsibility.

Skills SHOULD remain:

* reusable;
* composable;
* deterministic;
* narrowly scoped.

Skills SHOULD avoid orchestration.

---

# 9. Command

Commands expose Capabilities to users.

Commands SHALL remain lightweight.

Commands SHOULD delegate execution.

Commands SHOULD NOT contain business logic.

---

# 10. Validator

Validators verify outputs.

Validators SHALL never modify outputs.

Validation and transformation SHALL remain independent.

---

# 11. Generator

Generators create artifacts.

Examples:

* AED generation
* Documentation
* Specifications
* Code

Generators SHOULD remain deterministic whenever possible.

---

# 12. Analyzer

Analyzers inspect.

They SHOULD NOT mutate.

Analyzers answer questions.

They SHOULD avoid producing architectural changes.

---

# 13. Transformer

Transformers modify existing entities.

Transformers SHALL preserve contracts.

---

# 14. Template

Templates standardize output.

Templates SHALL remain implementation-independent.

Templates SHOULD contain no execution logic.

---

# 15. Capability Contract

Every Capability SHOULD expose the following information.

Purpose

Responsibilities

Inputs

Outputs

Dependencies

Preconditions

Postconditions

Failure Conditions

Consumers

Producers

Version

Owner

Review Cycle

Capabilities without contracts SHALL be considered incomplete.

---

# 16. Capability Lifecycle

Every Capability SHALL possess lifecycle.

Recommended states:

```text
Draft

↓

Experimental

↓

Stable

↓

Deprecated

↓

Archived
```

Execution state SHALL remain separate from lifecycle state.

---

# 17. Capability Composition

Capabilities SHOULD compose.

Large Capabilities SHOULD emerge through orchestration rather than growth.

Preferred:

```
Workflow

↓

Skill

↓

Validator

↓

Generator
```

Avoid:

One monolithic Capability performing every responsibility.

---

# 18. Capability Dependencies

Dependencies SHALL point toward more stable layers.

Capability

↓

Governance

↓

Knowledge

↓

Contracts

Capabilities SHALL never depend upon Runtime as permanent input.

---

# 19. Capability Discovery

Capabilities SHALL be discoverable.

Discovery SHALL occur through repository metadata.

Capabilities SHOULD NOT require directory traversal.

Capabilities SHALL describe themselves.

---

# 20. Capability Invariants

---

## CAP-001

Every executable Entity SHALL be a Capability.

---

## CAP-002

Every Capability SHALL expose one primary responsibility.

---

## CAP-003

Every Capability SHALL consume Governance.

---

## CAP-004

Every Capability SHALL consume Knowledge.

---

## CAP-005

Every Capability SHOULD expose a Contract.

---

## CAP-006

Capabilities SHALL remain composable.

---

## CAP-007

Capabilities SHALL remain replaceable.

---

## CAP-008

Capabilities SHALL remain model-independent.

---

# 21. Architectural Smells

The following indicate Capability degradation.

* Capabilities implementing governance.
* Capabilities redefining ontology.
* Commands containing business logic.
* Skills orchestrating workflows.
* Workflows implementing business logic.
* Monolithic Capabilities.
* Capabilities without contracts.
* Capabilities requiring undocumented assumptions.

These SHALL be progressively eliminated.

---

# 22. Future Evolution

Capability implementations MAY evolve.

Examples include:

* prompt-based execution;
* MCP integrations;
* native IDE actions;
* external APIs;
* autonomous planning systems;
* future execution runtimes.

The Capability abstraction SHALL remain stable regardless of implementation technology.

---

# 23. Decision

This AED establishes Capability as the canonical execution abstraction of the repository.

Future architectural evolution SHALL model executable behavior exclusively through Capabilities and their specialization hierarchy.

No new execution concept SHOULD be introduced unless it cannot be represented as a Capability.

---

# 24. Foundational Principle

> **Capabilities execute.**
>
> **Knowledge informs.**
>
> **Governance constrains.**
>
> **Contracts define.**
>
> **Ontology explains.**

Execution emerges from the collaboration of these independent architectural systems.

No single subsystem SHALL assume the responsibilities of another.
