# AED-00002

# Repository Operating Model

---

# Status

**Proposed**

Normative.

---

# 1. Purpose

This AED defines how the repository operates conceptually.

It intentionally avoids implementation details.

Instead, it specifies the responsibilities, interactions and operational boundaries between architectural domains.

Subsequent AEDs SHALL refine each domain independently.

---

# 2. Core Statement

The repository SHALL behave as an operating system rather than a document collection.

Artifacts SHALL collaborate.

They SHALL NOT exist merely as files stored inside directories.

Every artifact participates in a larger operating model.

---

# 3. Operating Philosophy

The repository SHALL expose five fundamental capabilities.

## 1.

Store knowledge.

---

## 2.

Govern behavior.

---

## 3.

Discover capabilities.

---

## 4.

Execute work.

---

## 5.

Preserve architectural consistency.

Every repository artifact MUST contribute to at least one of these capabilities.

Artifacts contributing to none SHOULD be removed.

---

# 4. Architectural Domains

The repository SHALL evolve around independent domains.

Domains are conceptual.

Physical directory structures MAY evolve.

Conceptual responsibilities SHALL remain stable.

---

## Domain A

# Core

Purpose:

Provide repository identity.

Responsibilities include:

* initialization
* discovery
* contracts
* registry
* bootstrapping

The Core SHALL remain intentionally small.

---

## Domain B

# Governance

Purpose:

Define immutable behavioral expectations.

Governance SHALL define:

* directives
* constraints
* policies
* standards
* ontology
* lifecycle

Governance SHALL never execute work.

---

## Domain C

# Knowledge

Purpose:

Represent repository knowledge.

Knowledge includes:

* architecture
* specifications
* decisions
* rationale
* glossary
* project memory

Knowledge SHALL remain implementation-independent.

---

## Domain D

# Capabilities

Purpose:

Represent what the repository knows how to do.

Capabilities include:

* agents
* skills
* workflows
* commands
* templates

Capabilities SHALL consume governance.

They SHALL NOT redefine governance.

---

## Domain E

# Runtime

Purpose:

Represent transient operational state.

Examples include:

* active sprint
* current task
* temporary decisions
* execution context

Runtime SHALL never become permanent documentation.

---

## Domain F

# Project

Purpose:

Represent business implementation.

Includes:

* source code
* tests
* documentation
* releases
* assets

Project artifacts SHALL remain independent from repository governance.

---

# 5. Repository Responsibilities

Every repository operation SHALL follow the same conceptual flow.

```text
Boot

↓

Discovery

↓

Knowledge

↓

Governance

↓

Capability Selection

↓

Execution

↓

Validation

↓

Persistence

↓

Completion
```

Skipping stages SHOULD be considered an architectural exception.

---

# 6. Repository Boot Sequence

Repository initialization SHALL become deterministic.

Boot SHALL progressively establish repository awareness.

Recommended sequence:

## Stage 1

Repository Identity

The agent understands:

* repository purpose
* repository scope
* repository version

Nothing more.

---

## Stage 2

Repository Discovery

The repository explains:

* where knowledge exists
* where governance exists
* where capabilities exist

The agent SHALL NOT search manually.

---

## Stage 3

Governance

Behavioral expectations become available.

---

## Stage 4

Capability Discovery

Executable capabilities become available.

---

## Stage 5

Execution

Only after previous stages complete.

---

# 7. Repository Discovery

Repository navigation SHALL be explicit.

Current generations of LLMs frequently explore directory trees.

Future repository architecture SHALL discourage exploration.

Preferred behavior:

Repository announces itself.

Agent consumes registry.

Agent loads required knowledge.

Agent executes.

Discovery SHALL replace inference.

---

# 8. Operational Flow

Every execution SHOULD conceptually follow this sequence.

## Question

What is being requested?

↓

## Classification

Which capability is required?

↓

## Governance

Which rules apply?

↓

## Knowledge

Which knowledge is required?

↓

## Execution

Perform work.

↓

## Validation

Verify outputs.

↓

## Completion

Persist results.

This flow SHOULD remain stable regardless of implementation.

---

# 9. Separation of Responsibilities

Repository components SHALL remain narrowly focused.

Examples:

Governance SHALL NOT execute.

Knowledge SHALL NOT prescribe behavior.

Capabilities SHALL NOT redefine policies.

Runtime SHALL NOT become documentation.

Project SHALL NOT redefine repository architecture.

Violations increase coupling.

---

# 10. Repository Dependency Rule

Dependency direction SHALL always point downward.

Conceptually:

```text
Execution

↓

Capabilities

↓

Governance

↓

Core
```

Higher layers MAY depend upon lower layers.

Lower layers SHALL NEVER depend upon higher layers.

---

# 11. Repository Gravity

Knowledge naturally accumulates.

Repository architecture SHALL continuously resist unnecessary growth.

Whenever new information is introduced, maintainers SHOULD ask:

* Does this already exist?
* Can it reference another artifact?
* Is this governance?
* Is this knowledge?
* Is this runtime?
* Is this implementation?

If uncertain, creation SHOULD be postponed.

---

# 12. Self-Describing Architecture

The repository SHALL progressively explain itself.

Agents SHOULD NOT require:

* tribal knowledge;
* onboarding documents;
* hidden assumptions;
* implicit conventions.

Repository understanding SHALL emerge from repository artifacts.

---

# 13. Repository Invariants

The following SHALL remain true throughout repository evolution.

---

## INV-001

Knowledge SHALL remain canonical.

---

## INV-002

Governance SHALL remain centralized.

---

## INV-003

Execution SHALL consume governance.

Execution SHALL NOT redefine governance.

---

## INV-004

Capabilities SHALL remain replaceable.

---

## INV-005

Repository architecture SHALL remain model-independent.

---

## INV-006

Directory layout SHALL never define semantics.

Semantics SHALL define directory layout.

---

## INV-007

Repository evolution SHALL continuously reduce entropy.

---

# 14. Anti-Patterns

The following patterns SHOULD be considered architectural smells.

* duplicated instructions
* duplicated prompts
* duplicated glossary entries
* duplicated workflows
* hidden conventions
* undocumented assumptions
* repository exploration as primary discovery
* prompts encoding governance
* commands redefining architectural rules
* project-specific knowledge inside reusable governance

Future refactoring SHOULD eliminate these progressively.

---

# 15. Expected Evolution

The repository is expected to evolve through four maturity stages.

## Stage 1

Prompt Repository

Knowledge concentrated in prompts.

---

## Stage 2

Governed Repository

Knowledge separated from execution.

---

## Stage 3

Operating Repository

Repository explains itself.

Capabilities become modular.

---

## Stage 4

Autonomous Repository

Repository becomes self-describing.

Agents require minimal onboarding.

Repository architecture remains stable across different runtimes.

This AED intentionally targets Stage 4.

---

# 16. Decision

This AED formally establishes the repository operating model.

Future architectural decisions SHALL preserve:

* deterministic boot;
* progressive discovery;
* governance before execution;
* capability modularity;
* explicit operational boundaries;
* self-describing architecture.

Subsequent AEDs SHALL define each domain independently without violating the operating model established herein.
